# Research: BayState Local Development Bootstrap

## Summary
BayState uses Supabase CLI for local DB/Auth, Stripe CLI for webhook forwarding, and Bun 1.3.5 + Turbo for the monorepo dev loop. The webhook handler uses `request.text()` + `constructEvent` correctly. 179 migrations exist but no `seed.sql`. The Stripe SDK is pinned to `2025-12-15.clover` API version. Vercel config uses `bun install --frozen-lockfile` with root project override. Key gaps: no seed data pipeline, no local Stripe CLI setup documented, `.env.local` has production values leaking into local dev, and `auth.site_url` in config.toml points to `127.0.0.1` instead of `localhost`.

## Findings

### 1. Supabase CLI Local Development

**1a. `supabase start`** — starts Docker containers for Postgres 17 (port 54322), API (54321), Studio (54323), Inbucket email (54324), and realtime. First run pulls images; subsequent runs are fast. Output prints local connection strings and service role keys. **Critical:** `supabase start` reads `config.toml` in the `supabase/` directory — the CLI must be run from `apps/web/` (where `supabase/config.toml` lives). [Supabase Docs: Local Dev](https://supabase.com/docs/guides/local-development/cli/getting-started)

**1b. `supabase db reset`** — drops all data, re-runs all migrations (in filename order from `supabase/migrations/`), then executes seed files if `[db.seed].enabled = true`. With 179 migrations this takes 30-90s. **Must have completed `supabase stop` first if containers are stale.** **Gotcha:** Granular migration errors are silent — only the failing migration number appears. Use `supabase migration list` and `supabase db diff` to debug. [Supabase Docs: db reset](https://supabase.com/docs/reference/cli/supabase-db-reset)

**1c. `config.toml`** — already correctly configured at `apps/web/supabase/config.toml`. Key settings:
- `project_id = "web"` — must match directory name
- `[auth].site_url = "http://127.0.0.1:3000"` — **should be `http://localhost:3000`** to match `NEXT_PUBLIC_SITE_URL` in `.env.local.example` (OAuth redirects fail if these disagree)
- `additional_redirect_urls` only includes `https://127.0.0.1:3000` — needs `http://localhost:3000/**` added
- `[db.seed].sql_paths = ["./seed.sql"]` — references a file that **does not exist**
- `[auth.email].enable_confirmations = false` — correct for dev; no email verification needed

**1d. `seed.sql`** — **missing.** `config.toml` references `./seed.sql` but no file exists at `apps/web/supabase/seed.sql`. Recommended content:
```sql
-- Seed: test user accounts (password: test-password-123)
INSERT INTO auth.users (email, encrypted_password, email_confirmed_at) VALUES
  ('admin@test.com', '$2a$10$...', now()),
  ('user@test.com', '$2a$10$...', now());

-- Seed: test product categories
INSERT INTO public.categories (name, slug) VALUES
  ('Dog Food', 'dog-food'),
  ('Cat Food', 'cat-food');
```
Use `supabase db reset` to apply seed after every reset. Store seed separately from migrations — migrations are for schema, seed is for data. [Supabase Docs: seeding](https://supabase.com/docs/guides/local-development/seeding)

**1e. Local Auth Redirect URLs** — must be added in Supabase Studio (localhost:54323) under Authentication → URL Configuration, or via `config.toml`:
```toml
[auth]
site_url = "http://localhost:3000"
additional_redirect_urls = [
  "http://localhost:3000/**",
  "http://127.0.0.1:3000/**"
]
```
Inbucket at `http://localhost:54324` captures all sent emails (magic links, password resets) in dev — no real emails sent.

**1f. 179+ Migrations Best Practices:**
- Name migrations `YYYYMMDDHHMMSS_description.sql` — timestamps enforce order. Already in place.
- Never edit an applied migration. Create a new one.
- Use `supabase db diff --file add_widgets_table` to auto-generate migration from local changes.
- Run `supabase migration list` to see which are applied vs pending.
- For large migration sets, wrap in transactions and add `-- migrate:up`/`-- migrate:down` comments. [Supabase Docs: migrations](https://supabase.com/docs/guides/local-development/cli/managing-migrations)

### 2. Stripe Local Development

**2a. Stripe CLI Installation & Login**
```bash
# macOS
brew install stripe/stripe-cli/stripe

# Verify
stripe --version

# Login (pairs CLI to Stripe account — test mode)
stripe login
```
Opens browser; after pairing, a `~/.stripe/config.toml` is created. [Stripe Docs: CLI](https://docs.stripe.com/stripe-cli)

**2b. `stripe listen --forward-to`**
```bash
stripe listen --forward-to http://localhost:3000/api/payments/webhook
```
This proxies real Stripe events (from your test-mode account) to the local Next.js server. The command prints a `whsec_...` signing secret on first run **once**. **Must restart on new terminal.** Gotcha: if the dev server isn't running, Stripe retries with exponential backoff for ~3 days — use `--skip-verify` for HTTPS localhost only if you have a self-signed cert. [Stripe Docs: webhook forwarding](https://docs.stripe.com/webhooks#local-listener)

**2c. Webhook Signing Secret (`whsec_`)**
- Printed once by `stripe listen` at startup: `> Ready! Your webhook signing secret is whsec_...`
- Set as `STRIPE_WEBHOOK_SECRET=whsec_...` in `.env.local`
- **Must restart Next.js after changing** — the Stripe SDK reads it at module initialization in `lib/payments/stripe.ts`
- The `constructWebhookEvent(body, signature, webhookSecret)` call in `app/api/payments/webhook/route.ts` validates this before processing — correct implementation.

**2d. PaymentIntent in Test Mode**
- API base is `https://api.stripe.com/v1` — same as production; just use `sk_test_*` key
- Current code uses `stripe.paymentIntents.create()` in `lib/payments/stripe.ts` with `automatic_payment_methods: { enabled: true }` and `amount: Math.round(amount * 100)` — correct (amount in cents, not dollars)
- **Gotcha:** The `createPaymentIntent` function sends `receipt_email` but Stripe will not send receipt emails in test mode — no-op, not an error.

**2e. Test Cards**
| Card | Result |
|------|--------|
| `4242 4242 4242 4242` | Succeeds (Visa) |
| `4000 0000 0000 0002` | Succeeds (Visa debit) |
| `4000 0025 0000 3155` | Requires 3D Secure |
| `4000 0000 0000 3220` | Requires 3D Secure (next gen) |
| `4000 0000 0000 9995` | Declined (insufficient funds) |

Use any future expiry date and any 3-digit CVC. [Stripe Docs: test cards](https://docs.stripe.com/testing#cards)

**2f. Webhook Idempotency Recommendations**
- Current handler **does not check idempotency** — Stripe may deliver the same event multiple times (at-least-once delivery).
- **Fix:** Store `stripe_event_id` (from `event.id`) in an `order_webhook_events` table with a unique constraint. Before processing, `SELECT 1 WHERE event_id = ...` — skip if exists.
- Alternative: use Stripe's `Idempotency-Key` header on the webhook response, but the DB check is more reliable.
- **CRITICAL:** `payment_intent.succeeded` delivered twice would try to update `payment_status` from `paid` to `paid` — idempotent enough for status, but `recordPaymentTransaction` would insert a duplicate row. **Idempotency guard on `order_payments` is essential.** [Stripe Docs: idempotency](https://docs.stripe.com/api/idempotent_requests)

### 3. Stripe PaymentIntent Best Practices

**3a. Server-Authoritative Amount (do not trust client)**
- Current implementation in `app/api/payments/intent/route.ts` accepts `amount` from the client body. **Vulnerable.** The amount should be recalculated server-side from the order total (from DB), not from the request body.
- **Recommendation:** require `orderId` in the request, fetch the order from DB, verify `amount === order.total * 100`. Return 400 if mismatch.

**3b. Metadata Best Practice**
Current metadata sent by `createPaymentIntent`:
```typescript
metadata: {
  customer_name: customerName,
  order_id: orderId || '',
  item_count: items.length.toString(),
  items: '...',
}
```
Missing critical fields:
- `order_number` — human-readable order reference
- `customer_email` — for Stripe dashboard searchability
- `environment` — `local`, `staging`, or `production` to distinguish in Stripe dashboard

**3c. Idempotency Keys**
- The `createPaymentIntent` call in `lib/payments/stripe.ts` does **not** pass an idempotency key.
- **Recommendation:** use `orderId` or a UUID as `idempotencyKey` in `stripe.paymentIntents.create()`. This prevents duplicate PaymentIntents if the API call is retried.
```typescript
const paymentIntent = await stripe.paymentIntents.create({
  amount,
  currency,
  ...
}, { idempotencyKey: `pi-${orderId}-${Date.now()}` });
```

**3d. Webhook as Source of Truth**
- Current architecture is correct: the `POST /api/payments/webhook` handler updates `orders.payment_status` from Stripe events.
- The payment intent creation endpoint returns `clientSecret` to the client — the client uses this to confirm with `stripe.confirmCardPayment()`.
- **After client-side confirm succeeds, the server must wait for the webhook** before marking the order as paid. Do not trust the client's "it worked!" — always wait for the Stripe-signed webhook.

**3e. Avoiding Duplicate PaymentIntents**
- Problem: if the user refreshes the checkout page and hits "Pay" again, a second PaymentIntent is created for the same order.
- **Recommendation:** check if an active PendingIntent already exists for the order (`SELECT stripe_payment_intent_id FROM orders WHERE id = ... AND payment_status = 'unpaid'`). If yes, retrieve and return its `client_secret` instead of creating a new one. Or cancel the old one first.

**3f. API Version Compatibility**
- Hardcoded `2025-12-15.clover` in `lib/payments/stripe.ts` and `createEphemeralKey`.
- The `.clover` suffix suggests a **Stripe Connect platform-specific version** — unlikely to be a standard Stripe API version (`2025-12-15` is a future date as of this writing).
- **Risk:** This version may not exist yet or may be a Connect-only preview. Using a future/nonexistent version can cause Stripe to silently use the latest stable version OR fail on some features.
- **Recommendation:** verify with `stripe.API_VERSION` (exported by the SDK) what version Stripe pin resolves to. Consider using a known stable version like `2025-02-24.acacia` (latest stable as of early 2025) or the SDK default. [Stripe Docs: API versioning](https://docs.stripe.com/api/versioning)

### 4. Next.js App Router Route Handlers

**4a. Raw Body Handling for Stripe Webhooks**
- Current code in `app/api/payments/webhook/route.ts` uses `request.text()` — **correct**.
- **Why not `request.json()`:** Stripe requires the raw body string for signature verification. `request.json()` parses the body, consuming the stream, making it unavailable for signature verification.
- The `constructWebhookEvent(body, signature, webhookSecret)` from the Stripe SDK takes the raw string — correct usage.

**4b. POST Handler Patterns**
- Current pattern (`export async function POST(request: NextRequest)`) is correct for App Router.
- Explicit 400 on missing `stripe-signature` header — good.
- Try/catch with `StripeSignatureVerificationError` handling — correct.
- **Gotcha:** `NextResponse.json()` returns a `NextResponse` object — no need to wrap in `new Response()`.
- **Gotcha:** the webhook handler uses `await createClient()` for each Supabase call instead of reusing a client — minor perf issue, not a correctness issue.

**4c. Environment Variables in API Routes**
- `process.env.STRIPE_WEBHOOK_SECRET` is checked at request time (not import time) — correct, allows hot-reload.
- **Gotcha:** if you set `STRIPE_WEBHOOK_SECRET` after server start, Next.js won't pick it up until restart. This is expected Next.js behavior.
- `process.env.STRIPE_SECRET_KEY` is read at module import time in `lib/payments/stripe.ts` — if missing, a warning is printed and a placeholder is used. This means API calls using the `stripe` instance will fail with auth errors, not graceful "not configured" messages. **Recommendation:** use lazy initialization or check before each call.

### 5. Vercel + Bun + Monorepo Deployment

**5a. Root Project vs App Root**
- `vercel.json` at repo root sets the project root implicitly (Vercel auto-detects Next.js).
- `buildCommand: "bun run build"` runs from the **vercel project root**, which is the monorepo root.
- `package.json` at root has `"vercel-build": "cd apps/web && next build"` but `vercel.json` overrides this with `buildCommand: "bun run build"`.
- **This is a conflict:** `bun run build` at repo root runs `turbo run build`, which detects the workspace, runs `apps/web:build` → `next build`. This works with Turbo's monorepo support.
- **Gotcha:** Turbo must be in `devDependencies` of root `package.json` (it is: `"turbo": "^2.8.17"`). Vercel needs `ENABLE_BUN_INSTALL=1` in environment (currently set in `.env.local` — needs to be in Vercel project env vars too).

**5b. Build/Install Command Expectations**
- `installCommand: "bun install --frozen-lockfile"` in `vercel.json` — correct.
- `ignoreCommand: "bunx turbo-ignore"` — uses Turbo's built-in skip-if-no-changes detection.
- **Root-level `bun run build` runs root `build` script → `turbo run build` → runs `apps/web:build` → `next build`.**
- **Gotcha:** If `turbo.json` `build` task has `dependsOn: ["^build"]`, it waits for dependency packages to build first. The `@baystate/api` workspace package in `packages/api` must have its own `build` script and `turbo.json` `build` config.
- **Gotcha:** `bun install --frozen-lockfile` requires an existing `bun.lock` file. If lockfile is missing or out of date, deployment fails. [Vercel Docs: Bun](https://vercel.com/docs/deployments/configure-a-build#bun)

**5c. Environment Variables**
- Vercel project env vars override `.env.local` values.
- **Current `.env.local` has production/staging values** (`SUPABASE_URL` is a production Supabase URL, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` is a test key — mixed). This is dangerous for local dev — local dev should use `http://localhost:54321` for Supabase, not `https://fapnuczapctelxxmrail.supabase.co`.
- **Recommendation:** create `.env.local` for local values, `.env.production` for Vercel-injected values. Vercel dashboard env vars take precedence over both.

**5d. `turbo.json` Configuration**
Current `turbo.json`:
```json
{
  "tasks": {
    "dev": { "cache": false, "persistent": true },
    "build": {
      "dependsOn": ["^build"],
      "env": ["VERCEL", "NEXT_PUBLIC_SUPABASE_URL", "NEXT_PUBLIC_SUPABASE_ANON_KEY"],
      "outputs": [".next/**", "!.next/cache/**", ".vercel/output/**", "dist/**"]
    },
    "test": { "dependsOn": ["build"], "outputs": [] },
    "lint": { "outputs": [] },
    "typecheck": { "dependsOn": ["^typecheck"], "outputs": [] }
  }
}
```
- `build.env` only declares 3 vars — any other env vars needed at build time (`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, etc.) should be added or Turbo will skip cache invalidation when they change (minor, causes stale builds).
- **`test` depends on `build`** — this makes `bun run test` run a full build first. For CI this is intentional, but for local dev `bun run web test` (which runs `cd apps/web && node scripts/run-jest.cjs`) bypasses Turbo entirely.
- **Gotcha:** `dev` is marked `persistent: true` — this tells Turbo it's a long-running server. Correct for `next dev`. [Turbo Docs: tasks](https://turbo.build/repo/docs/core-concepts/tasks)

## Gaps

1. **No seed.sql exists** — `config.toml` references `./seed.sql` but file is missing. Makes `supabase db reset` useless for populating test data.
2. **API version `2025-12-15.clover`** — unverifiable as a standard Stripe API version. Need to confirm with Stripe docs or SDK introspection.
3. **Missing idempotency** — webhook handler has no dedup guard; `order_payments` can get duplicate rows on retried webhook delivery.
4. **Client-authoritative amount** — `/api/payments/intent` accepts `amount` from client without server-side verification against DB order total.
5. **No duplicate PaymentIntent guard** — refreshing checkout page can create multiple PaymentIntents for the same order.
6. **Mixed production/test environment variables** in `.env.local` — local Supabase URL is production, not localhost:54321.
7. **No documented Stripe CLI bootstrap** — no script or README section for `stripe login && stripe listen`.
8. **Vercel build command ambiguity** — `vercel.json` says `bun run build` but root `package.json` has `vercel-build` script that also works; only one is actually used.
