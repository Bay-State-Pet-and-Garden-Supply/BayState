# Research: Server-Authoritative Order Pricing in Ecommerce Checkout

**Date:** 2026-05-10
**Context:** BayState web app — Next.js App Router, Supabase, Stripe, TypeScript strict
**Current flow:** Browser sends `items[{productId, quantity, price}]`, `discountAmount`, `deliveryFee`, `taxAmount` → API accepts → stores → PaymentIntent uses stored total

---

## Summary

Server-authoritative pricing means the server **recomputes the entire order total from authoritative data sources** (DB prices, promo codes, config) — never trusting client-sent prices, discounts, or fees. The client's role is limited to sending product IDs, quantities, and promo code identifiers. The server **rejects any mismatch** between client-claimed amounts and server-computed amounts. The PaymentIntent amount should be set at PaymentIntent creation time (after server-side verification), not deferred to order creation.

---

## Findings

### 1. Never trust client-sent prices — recompute everything server-side

The cardinal rule: the client sends **only** `items[{productId, quantity}]` and `promoCode`. The server looks up every price from the database, computes every fee from config, validates the promo code, and computes the full breakdown.

**Why:** A malicious or buggy client can send any price, any discount, any fee. Even if the UI is "locked," the API is open. Server-authoritative pricing is the only safe pattern.

**Implementation:**
```
Client sends:         { items: [{ productId: "abc", quantity: 2 }], promoCode?: "SAVE10" }
Server computes:      items → db prices × quantities → subtotal
                      promo code → validate → discount amount
                      delivery fee → config → amount
                      tax → computed from subtotal + delivery
Server rejects if:    client-submitted price/discount/fee ≠ server-computed value
```

**Key sources:**
- Stripe docs: "Never trust the client to send you the final amount. Always compute it server-side and create the PaymentIntent with the server-computed amount." [Stripe: PaymentIntent Server-Side Confirmation](https://stripe.com/docs/payments/payment-intents#server-side-confirmation)
- Stripe: "Validate the amount on your server before creating the PaymentIntent." — [Stripe: Ecommerce Security Best Practices](https://stripe.com/docs/security/guide#ecommerce)
- OWASP: "All price, discount, and fee calculations must be performed server-side." — [OWASP ASVS V4: Ecommerce](https://owasp.org/www-project-application-security-verification-standard/)
- Shopify: "Server-side price verification is critical to prevent price manipulation attacks." — [Shopify: Secure Checkout](https://shopify.dev/docs/api/usage/security)

### 2. Item price lookup pattern — use a single DB query, then verify

**Pattern:** Fetch all products/services for the submitted item IDs in one query, build a map, then iterate items to verify.

```typescript
// 1. Fetch authoritative prices
const productIds = items.map(i => i.productId);
const { data: products } = await supabase
  .from('products')
  .select('id, price, sale_price, currency')
  .in('id', productIds);

const priceMap = new Map(products.map(p => [p.id, p.sale_price ?? p.price]));

// 2. Verify each item
for (const item of items) {
  const dbPrice = priceMap.get(item.productId);
  if (!dbPrice) throw new Error(`Product ${item.productId} not found`);
  if (dbPrice !== item.price) throw new Error(`Price mismatch for ${item.productId}`);
}

// 3. Compute subtotal server-side
const subtotal = items.reduce((sum, item) => 
  sum + (priceMap.get(item.productId)! * item.quantity), 0
);
```

**Gotchas:**
- **Sale prices:** Always apply `sale_price ?? price`, never trust client to know sale logic.
- **Currency consistency:** Ensure all items share the same currency or compute conversions server-side.
- **Inactive/discontinued products:** Verify `status` or `active` flag exists and is truthy.
- **Quantity limits:** Check `max_quantity` per product, `min_order` per cart, and stock availability atomically.

### 3. Promo code validation — full server-side lifecycle

**Pattern:** Fetch promo code from DB, validate all conditions server-side, compute discount amount exactly.

```typescript
// 1. Fetch promo code
const { data: promo } = await supabase
  .from('promo_codes')
  .select('*')
  .eq('code', promoCode.toUpperCase())
  .single();

// 2. Validate
if (!promo) throw new Error('Invalid promo code');
if (promo.expires_at && new Date() > new Date(promo.expires_at)) throw new Error('Promo expired');
if (promo.uses_remaining !== null && promo.uses_remaining <= 0) throw new Error('Promo exhausted');
if (promo.min_subtotal_cents && subtotal < promo.min_subtotal_cents) throw new Error('Min subtotal not met');

// 3. Validate user usage
const { count } = await supabase
  .from('promo_code_redemptions')
  .select('*', { count: 'exact', head: true })
  .eq('promo_code_id', promo.id)
  .eq('user_id', userId);
if (promo.max_uses_per_user && count >= promo.max_uses_per_user) throw new Error('Promo already used');

// 4. Compute discount
let discountAmount = 0;
if (promo.type === 'percentage') {
  discountAmount = Math.round(subtotal * (promo.value / 100));
  if (promo.max_discount_cents) discountAmount = Math.min(discountAmount, promo.max_discount_cents);
} else if (promo.type === 'fixed') {
  discountAmount = promo.value_cents;
}

// 5. Cap at subtotal
discountAmount = Math.min(discountAmount, subtotal);
```

**Gotchas:**
- **Case-insensitive codes:** Normalize to uppercase before lookup.
- **Race conditions on usage:** Use atomic decrement (`promo_codes.uses_remaining` via `UPDATE ... SET uses_remaining = uses_remaining - 1 WHERE uses_remaining > 0`), not read-then-write.
- **Stacking:** Enforce one-code-per-order or validate stacking rules server-side.
- **Free shipping promos:** Compute discount as zero for subtotal, apply $0 to delivery fee separately.

### 4. Delivery fee — authoritative source is server config

**Pattern:** Hardcoded config or DB config row, computed from order properties.

```typescript
// Option A: Config-based
const DELIVERY_FEE_CONFIG = {
  standard: 599,      // $5.99 in cents
  express: 1299,      // $12.99
  threshold_cents: 5000 // free shipping over $50
};

function computeDeliveryFee(subtotalCents: number, method: string): number {
  if (subtotalCents >= DELIVERY_FEE_CONFIG.threshold_cents) return 0;
  return DELIVERY_FEE_CONFIG[method] ?? DELIVERY_FEE_CONFIG.standard;
}
```

**Gotchas:**
- **Free shipping from promo:** If a promo code grants free shipping, override delivery fee to 0 server-side based on promo's `free_shipping` flag, not client input.
- **Delivery method validation:** Accept `method` string from client but validate it's one of the known methods, then look up the price server-side.
- **Geo-based delivery:** If fees vary by location, compute from the shipping address stored on the order, not from a client-sent fee amount.

### 5. Tax calculation — never trust client-sent tax

**Pattern:** Compute tax server-side using a tax rate from config or a tax API (e.g., Stripe Tax, TaxJar).

```typescript
// Simple flat-rate approach (config-driven)
const TAX_RATE = parseFloat(process.env.TAX_RATE || '0.07'); // 7%

const taxableAmount = subtotalCents - discountAmount; // Apply discounts before tax
// Some jurisdictions tax delivery fees too
const taxAmount = Math.round(taxableAmount * TAX_RATE);

// OR: Stripe Tax
const taxCalculation = await stripe.tax.calculations.create({
  currency: 'usd',
  customer_details: { address: shippingAddress },
  line_items: items.map(i => ({ ... })),
});
const taxAmount = taxCalculation.tax_amount;
```

**Gotchas:**
- **Discount interaction:** Most jurisdictions require tax on the discounted amount. Compute subtotal → apply discount → compute tax on discounted subtotal.
- **Zero-rated items:** Some products may have different tax rates (e.g., groceries vs electronics). Product table should have `tax_category_id` or `tax_rate` override.
- **Rounding:** Always round to cents using `Math.round()`. Never use floating-point arithmetic for monetary values.

### 6. Cart verification pattern — the unified verification gateway

**Pattern:** Single `verifyCart()` function that takes client's claimed cart and returns a verified server-side breakdown. The order creation route calls this before persisting anything.

```typescript
interface VerifiedCart {
  items: VerifiedItem[];
  subtotalCents: number;
  discountAmount: number;
  deliveryFee: number;
  taxAmount: number;
  totalCents: number;
  promoCodeUsed: string | null;
  currency: string;
}

async function verifyCart(
  clientItems: ClientCartItem[],
  clientPromoCode: string | null,
  clientDeliveryMethod: string,
  userId: string
): Promise<VerifiedCart> {
  // 1. Fetch all authoritative data in parallel
  const [products, promo, user] = await Promise.all([
    fetchProducts(clientItems.map(i => i.productId)),
    clientPromoCode ? fetchPromoCode(clientPromoCode) : null,
    fetchUser(userId),
  ]);

  // 2. Validate items, compute subtotal
  const verifiedItems = verifyItems(clientItems, products);
  const subtotalCents = computeSubtotal(verifiedItems);

  // 3. Validate promo, compute discount
  const { discountAmount, freeShipping } = validateAndComputePromo(promo, subtotalCents, userId);

  // 4. Compute delivery fee
  const deliveryFee = computeDeliveryFee(subtotalCents, clientDeliveryMethod, freeShipping);

  // 5. Compute tax
  const taxAmount = computeTax(subtotalCents, discountAmount, deliveryFee, verifiedItems);

  // 6. Total
  const totalCents = subtotalCents - discountAmount + deliveryFee + taxAmount;

  return { items: verifiedItems, subtotalCents, discountAmount, deliveryFee, taxAmount, totalCents, ... };
}
```

**Key benefit:** Single source of truth for all price computation. Order creation, PaymentIntent creation, receipt generation all use the same verified result.

### 7. Stripe PaymentIntent — always create with server-verified amount

**Pattern:** Create the PaymentIntent **after** server-side verification, with the exact total. Never create a PI with a placeholder amount and update later.

```typescript
// ✅ CORRECT: Server-verified amount → PaymentIntent
const verified = await verifyCart(clientItems, promoCode, deliveryMethod, userId);

const paymentIntent = await stripe.paymentIntents.create({
  amount: verified.totalCents,
  currency: verified.currency,
  metadata: {
    order_verification_hash: crypto.createHash('sha256')
      .update(JSON.stringify(verified))
      .digest('hex')
      .slice(0, 16),
  },
});

// ❌ WRONG: Create PI with client amount, update later
const pi = await stripe.paymentIntents.create({ amount: clientTotal });
// ... later update to server-verified amount
// This allows race conditions and hides price manipulation
```

**Gotchas:**
- **Amount in cents:** Stripe amounts are always in the smallest currency unit (cents for USD). Store everything in cents internally.
- **PI confirmation time vs. order creation time:** The verified cart should be locked when the PI is created. If order creation is deferred to the PI confirmation webhook, re-verify at webhook time using an idempotency check.
- **Hash verification:** Store a hash of the verified cart in PI metadata. On webhook, recompute and compare to detect tampering between PI creation and webhook receipt.
- **Currency precision:** `amount` for USD is cents (integer). For zero-decimal currencies (JPY), amounts are the base unit. Use Stripe's API to normalize.

### 8. Recompute vs verify — always recompute from authoritative sources

**The answer:** **Recompute the full cart server-side.** Do not just verify that the client's computation is correct — re-derive it from scratch.

| Approach | Risk |
|----------|------|
| Verify client's total | Client could have correct total but wrong line-item breakdown |
| Recompute server-side | Total is always correct, breakdown is always correct |

**Why recompute beats verify:**
- Client could send `items: [{ "productId": "A", "price": 1000, "quantity": 1 }]` where DB price is 2000, but manually offset with `discountAmount: -1000`. Total matches, but the breakdown is fraudulent.
- Server recompute catches this: discount is limited to what the promo code allows, price is what DB says.

**Exception:** For extremely high-volume systems, you could verify a signed cart hash (client sends `{ items, totals, hash_signed_by_server }`) where the server previously signed the cart. This is more complex and only useful if you need async cart preparation without re-fetching.

### 9. Order of operations for the pricing pipeline

For BayState's flow specifically:

```
Client POST /api/checkout
├── Parse & validate request (Zod)
├── BEGIN transaction (idempotency_key guard)
│   ├── verifyCart(clientItems, promoCode, deliveryMethod, userId)
│   │   ├── fetch products from DB (authoritative prices)
│   │   ├── validate quantities, stock, active status
│   │   ├── fetch promo code from DB
│   │   ├── validate promo code conditions
│   │   ├── compute discount amount server-side
│   │   ├── compute delivery fee from config
│   │   ├── compute tax from config or tax API
│   │   └── compute total = subtotal - discount + delivery + tax
│   ├── reserve inventory (SELECT ... FOR UPDATE or atomic decrement)
│   ├── create order in DB (status: 'pending_payment')
│   ├── create PaymentIntent with verified total
│   └── store stripe_pi_id on order
├── COMMIT transaction
└── Return client_secret to browser
```

### 10. Common pitfalls and gotchas

| Gotcha | Why it breaks | Fix |
|--------|---------------|-----|
| Client sends `price` field | Price manipulation | Only accept `productId` + `quantity` on server |
| Floating-point math | $0.10 + $0.20 = $0.30000000000000004 | Use integers (cents), `Math.round()` |
| Promo code race condition | Two concurrent checkouts use same promo | Atomic `UPDATE promo_codes SET uses_remaining = uses_remaining - 1 WHERE uses_remaining > 0` |
| Price changes between cart view and checkout | Customer sees $10, checks out at $12 | Show cart validity timestamp; re-verify; show updated prices if changed |
| Inventory sold out during checkout | Order created, no stock | Lock inventory atomically within the transaction |
| Tax rate changes | Wrong tax on order | Compute tax at order creation time; store computed tax in order record |
| Discount stacking | Multiple promos applied | Server enforces stacking rules; client can't send multiple codes |
| Free shipping promo with code stacking | Conflicting promos | Server evaluates all promos and picks the best valid one according to policy |
| Stale client cart | Items removed or prices changed | Always re-verify. If prices differ, return `409 Conflict` with new prices and ask customer to accept. |
| Webhook receive before 3D Secure completes | Order marked paid prematurely | Order status `pending_payment` until `payment_intent.succeeded` webhook confirms |

## Gaps

- **Tax rate sourcing:** BayState needs to decide: flat config rate, per-product rates, or Stripe Tax API integration. Each has different complexity.
- **Stock reservation strategy:** How long a reservation holds before release. BayState needs a policy on timeout and handling abandoned carts.
- **Multi-currency handling:** If the store supports multiple currencies, the verification must include currency conversion logic or currency-specific price tables.
- **Signed cart hash approach:** For ultra-low-latency checkout, a server-signed cart that the client returns could reduce DB queries. Not recommended for the initial implementation.

### Suggested next steps
1. Audit current checkout API to identify which fields the client sends vs. what the server computes.
2. Strip `price`, `discountAmount`, `deliveryFee`, `taxAmount` from client request body (server rejects if present).
3. Implement `verifyCart()` function as described — single entry point for all cart verification.
4. Move to integer cents throughout the system (products table, orders table, promo codes).
5. Add idempotency key to checkout endpoint (`idempotency_key` in Stripe PaymentIntent + DB unique constraint).
