## Current Order Creation Flow

### Step-by-step data flow:

#### 1. Product page → Cart store
- `AddToCartButton` receives `product.price` rendered from DB (`products.price` column).
- Passes `price: product.price` to `useCartStore.addItem()` → stored in Zustand (persisted to localStorage).
- **This price is correct at time of page render, but stale if price changes before checkout.**

#### 2. Checkout page (client-side computation)
- `checkout-client.tsx` reads prices from Zustand cart store (which came from the page SSR).
- Computes on the client:
  ```typescript
  subtotal // from cart store getSubtotal()
  discount // from cart store getDiscount()
  discountedSubtotal = Math.max(0, subtotal - discount)
  tax = discountedSubtotal * TAX_RATE // 0.0625 (hardcoded in lib/types.ts)
  total = discountedSubtotal + tax + deliveryFee
  ```
- Calls `getDeliveryQuote()` client-side (uses Mapbox geocoding + hardcoded fee config).
- Promo validation is done server-side via `POST /api/promo/validate`, returns `discount` amount + `discountType`.
- Discount amount is stored in Zustand and sent to the API.

#### 3. Browser → API (`POST /api/orders`)
Client sends in request body:
```json
{
  "items": [{ "id", "name", "slug", "price", "quantity", ... }],
  "discountAmount": 10.00,
  "deliveryFee": 32.50,
  "deliveryServices": ["pallet_jack"],
  "fulfillmentMethod": "delivery",
  "customerName", "customerEmail", ...
}
```
**The Zod schema accepts `items[i].price` without verification.**

#### 4. API route → `createOrder()`
- `createOrder()` in `lib/orders.ts` recalculates:
  ```typescript
  subtotal = items.reduce((s, i) => s + i.price * i.quantity, 0)  // Uses client price
  discountAmount = input.discountAmount || 0                      // From client
  deliveryFee = input.deliveryFee || 0                            // From client
  discountedSubtotal = Math.max(0, subtotal - discountAmount)
  tax = discountedSubtotal * 0.0625                               // Hardcoded
  total = discountedSubtotal + tax + deliveryFee
  ```
- Inserts order and order_items into DB with these computed values.
- Does NOT re-validate promo code, delivery fee, or item prices against DB.

#### 5. Post-order: Payment Intent
- `POST /api/payments/intent` reads `order.total` from the DB (the stored value from step 4).
- Creates Stripe PaymentIntent with that amount.
- **This means Stripe charges what the client said, stored in step 4.**

## Security Gap: Server Trusts Client on These Values

The server blindly accepts these **attack surface** inputs from the client:

| Client-provided field | Risk |
|-----------------------|------|
| `items[i].price` | User can modify to any value before POST |
| `items[i].quantity` | Trusted (could validate against stock) |
| `discountAmount` | User can claim any discount amount |
| `deliveryFee` | User can set to $0 or negative |
| `deliveryServices` | User can claim free services |
| `promoCode` / `promoCodeId` | User could use expired/invalid code |

## What Would Need to Change for Server-Authoritative Pricing

### Phase 1: Product/Service Price Re-verification (Core Fix)

In `createOrderWithClient()` (or the API route before calling it), **re-fetch product prices from DB** instead of using client values:

1. **API route** (`app/api/orders/route.ts`):
   - After Zod validation, call a server-side verification function.
   - Build a list of `item_id` values, split into products vs services.

2. **New server-side verification** (could be in `lib/orders.ts` or a new `lib/pricing.ts`):
   - Fetch all referenced products: `SELECT id, price FROM products WHERE id IN (...)`
   - Fetch all referenced services: `SELECT id, price FROM services WHERE id IN (...)`
   - Verify each `items[i].price` matches the DB `price` column.
   - Fail/reject if mismatch detected.

### Phase 2: Promo Code Re-verification

- Call `validatePromoCode()` server-side during order creation (re-validate the promo code and recalculate discount).
- The promo code ID must be verified against the actual code and current subtotal.
- Store `promo_code_id` FK properly (it's already nullable FK).

### Phase 3: Delivery Fee Re-verification

- Re-implement or reuse `getDeliveryQuote()` server-side with:
  - Address geocoding (Mapbox API call from server).
  - Distance calculation.
  - Fee computation using same config.
- Compare computed total delivery fee with client-provided value.
- Options:
  - **Strict**: Reject if mismatch.
  - **Graceful**: Override client value with server-computed value (silent correction).

### Phase 4: Tax Re-verification

- Tax rate is hardcoded (MA 6.25%). This could stay hardcoded or moved to env/DB config.
- Recompute server-side: `Math.round(discounted_subtotal * TAX_RATE * 100) / 100`

### Phase 5: Final Total Re-computation

After all individual components are verified:
```typescript
const serverSubtotal = verifiedItems.reduce(...)
const serverDiscount = recalculatedPromoDiscount
const serverDiscountedSubtotal = Math.max(0, serverSubtotal - serverDiscount)
const serverTax = Math.round(serverDiscountedSubtotal * TAX_RATE * 100) / 100
const serverDeliveryFee = recalculatedDeliveryFee
const serverTotal = Math.round((serverDiscountedSubtotal + serverTax + serverDeliveryFee) * 100) / 100
```
Override ALL client-provided pricing fields with server-computed values before inserting to DB.

### Phase 6: Stripe PaymentIntent Already Secure

The payment intent creation already reads `order.total` from DB (after storage). This is good. But since the order was stored with client-trusted data, it's currently a "garbage in, garbage out" situation. After Phases 1-5, the stored total is server-authoritative, so the stripe intent amount is also correct.

## Complexity Assessment

| Component | Complexity | Effort Estimate |
|-----------|------------|-----------------|
| Product/service price verification | **Low** | 1-2 days |
| Promo code re-verification | **Low** | 0.5-1 day |
| Delivery fee re-verification | **Medium** | 2-3 days (Mapbox API calls, server-side geocoding dependency) |
| Tax re-computation | **Trivial** | <2 hours |
| Total re-computation & override | **Trivial** | <1 hour |
| Testing (unit + integration + security) | **Medium** | 2-3 days |
| **Total** | **Small-to-Medium refactor** | **~1 week** |

### Risk factors:
- **Mapbox API dependency**: The delivery quote function uses Mapbox geocoding + distance matrix. If this runs inside the API route (in the request lifecycle), it adds latency (~500ms-2s) and could fail (user address not found, API rate limits). Consideration: accept the delivery fee from client but verify it's within expected bounds (e.g., within 5mi range rounding tolerance), or pre-validate during the checkout flow and pass a verified quote token.
- **Rounding differences**: Client-side JS and server-side JS should produce identical results for the same inputs, but need to ensure `Math.round(amount * 100) / 100` pattern is used consistently.
- **Edge cases**: Preorder batches, free shipping promo codes, pickup (zero delivery fee), partial refunds.

---

## Conclusion

**Verdict: Small refactor (not large).** The architecture is straightforward:
- Pricing calculation is centralized in `createOrderWithClient()` — single function to add verification to.
- All authoritative data sources exist in the DB.
- The delivery fee calculation is already in a shared library `lib/storefront/delivery.ts` that can be called from both client and server.
- The payment intent creation already re-reads from DB (partially secure).

The main change is adding a verification step between the API route's Zod validation and the `createOrder()` call. Recommended approach: create a new `lib/pricing/verify.ts` module that takes the client's desired items/promo/delivery params and returns either (a) verified pricing to store or (b) a rejection error.
