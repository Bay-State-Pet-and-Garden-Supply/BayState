# Staged Implementation Plan (Post-Oracle)

## Decisions
- **Checkout token deferred.** Too much API/schema/UI change for this pass.
- **Server-authoritative pricing partially deferred.** PaymentIntent will verify client amount against stored order total, but full server-side recomputation of items/delivery/promos is out of scope for this pass. Residual risk documented in final report.
- **Staged execution.** Worker implements Stage 1 + Stage 2 + Stage 4 in one pass. Stage 3 (checkout UI) only if changes are minimal.

## Stage 2: Stripe Hardening (Helper, PI Route, Webhook, Payment-Complete)

### 2.1 Stripe helper
- `lib/payments/stripe.ts`:
  - Replace module-level client with `getStripeServerClient()` that throws if `STRIPE_SECRET_KEY` missing/placeholder.
  - Reject `sk_live_` in non-production.
  - Keep explicit API version but verify against SDK.
  - Add `centsFromDollars()` helper.
  - Add `getOrCreatePaymentIntent()` with idempotency key `order:{orderId}:payment-intent`.

### 2.2 PaymentIntent route
- `app/api/payments/intent/route.ts`:
  - Accept `{ orderId }` only (no amount/items from client).
  - Load order + items server-side via admin client.
  - Compute/verify amount from `order.total`.
  - Reject if order already paid/refunded/voided.
  - Reuse existing active PI if `stripe_payment_intent_id` exists and amount/currency match.
  - Create new PI with metadata: `order_id`, `order_number`, `customer_email`, `environment`.
  - Store `stripe_payment_intent_id` on order.
  - Return clear errors for missing Stripe config or invalid order state.

### 2.3 Webhook route
- `app/api/payments/webhook/route.ts`:
  - Use `request.text()` for raw body.
  - Verify signature with `STRIPE_WEBHOOK_SECRET`.
  - Before processing, insert event ID into `stripe_webhook_events` with status `processing`.
  - On conflict, return 200 `{ received: true, duplicate: true }` only if previous was `processed` or `skipped`.
  - If previous was `failed`, retry processing (update to `processing` and continue).
  - Handle: `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `charge.refunded`.
  - Use shared reconciliation logic.
  - Update event row to `processed`, `skipped`, or `failed`.

### 2.4 Migration: webhook idempotency
- `supabase/migrations/20260510210000_stripe_webhook_idempotency.sql`:
  - Create `stripe_webhook_events` table with `event_id text primary key`, `event_type`, `stripe_object_id`, `order_id`, `status` (`processing|processed|skipped|failed`), `received_at`, `processed_at`, `error_message`, `payload jsonb`.
  - Enable RLS, service-role manage policy, staff read policy.
  - Add `stripe_event_id text` to `order_payments` with unique partial index on non-null.

### 2.5 Payment-complete endpoint
- `app/api/orders/[id]/payment-complete/route.ts`:
  - Accept `{ paymentIntentId }`.
  - Load order server-side.
  - Retrieve PI from Stripe server-side.
  - Verify `paymentIntent.metadata.order_id === orderId`.
  - Verify `paymentIntent.status === 'succeeded'`.
  - Verify amount matches order total.
  - Call shared reconciliation (idempotent).
  - Return current order payment status.

### 2.6 Shared reconciliation helper
- `lib/payments/order-payment-reconciliation.ts`:
  - Map Stripe events to order payment status.
  - Upsert `order_payments` with `stripe_event_id`.
  - Insert `order_events` only on actual status change.
  - No downgrade from `paid/refunded` to `failed`.
  - Refund amount uses Stripe cumulative amount carefully.

## Things Worker Must NOT Do
- Do not commit `.env.local` or real secrets.
- Do not seed production data/credentials.
- Do not trust client amount, item price, discount, delivery fee, or paid status.
- Do not mark paid from browser claims alone.
- Do not skip retry for failed webhook processing.
- Do not insert raw Stripe payment method IDs into constrained DB fields.
- Do not rewrite checkout broadly.
- Do not edit old migrations.
- Do not claim validation unless commands actually ran.
- Do not add checkout token columns.
- Do not spawn subagents.
