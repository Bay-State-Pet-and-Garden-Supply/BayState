### File to Create

**`apps/web/supabase/migrations/20251230175000_create_products_ingestion.sql`**

```sql
-- Backfill: Create products_ingestion table that was bootstrapped outside the migration system.
-- This table is referenced by 26 downstream migrations but was never formally created in one.
-- CREATE TABLE IF NOT EXISTS ensures idempotency for databases that already have the table.

CREATE TABLE IF NOT EXISTS public.products_ingestion (
    sku text PRIMARY KEY,
    input jsonb DEFAULT '{}'::jsonb,
    consolidated jsonb DEFAULT '{}'::jsonb,
    sources jsonb DEFAULT '{}'::jsonb,
    b2b_sources jsonb DEFAULT '{}'::jsonb,
    enrichment_config jsonb DEFAULT '{}'::jsonb,
    active_consolidation_review_id uuid,
    consolidation_review_status text DEFAULT 'pending',
    consolidation_review_updated_at timestamptz,
    pipeline_status text DEFAULT 'imported',
    created_at timestamptz DEFAULT now(),
    updated_at timestamptz DEFAULT now()
);

-- Index for pipeline_status queries (used by earliest view and all pipelines)
CREATE INDEX IF NOT EXISTS idx_products_ingestion_pipeline_status 
ON public.products_ingestion(pipeline_status);

-- Index for SKU lookups
CREATE INDEX IF NOT EXISTS idx_products_ingestion_sku 
ON public.products_ingestion(sku);
```

### Why `pipeline_status text` not enum
- `pipeline_status_five` enum is created at `20260319120000` (timeline: 2026-03-19)
- Our backfill is `20251230175000` (timeline: 2025-12-30) — enum doesn't exist yet
- `text` matches what `20251230180000` view expects in its `WHERE` clause
- Later migration `20260412011500` handles type conversion: `ALTER COLUMN pipeline_status TYPE text ... TYPE pipeline_status_five`

### Why `b2b_sources`, `enrichment_config`, etc. are included
- These columns exist in the TypeScript types (`database.types.ts`) and are referenced by app code
- They were NEVER added by any migration — they were part of the original bootstrapped table
- Not including them means a fresh `db reset` would create a table missing columns that app code expects
- `CREATE TABLE IF NOT EXISTS` is a harmless no-op on production (table already has them)

### Risk
- **Low.** `CREATE TABLE IF NOT EXISTS` is idempotent. No existing migration files modified — zero checksum risk.
- Migration timestamp `20251230175000` sits between last safe migration (`20251230170000_site_settings`) and first failing reference (`20251230180000_products_published_view`).

## BLOCKER 2: Server-Authoritative Order Pricing

### Problem Summary
The order creation flow trusts client-provided prices, discounts, delivery fees, and tax amounts. A malicious or buggy client can manipulate any of these values. The PaymentIntent is created with the stored (client-trusted) total, so Stripe charges whatever the client claimed.

### Current Architecture (Attack Surface)

```
Browser sends POST /api/orders:
{
  items: [{ id, name, slug, price, quantity, ... }],   ← price from client
  discountAmount: 10.00,                                 ← from client (Zustand)
  deliveryFee: 32.50,                                    ← from client (Mapbox quote)
  promoCode, promoCodeId,
  fulfillmentMethod, ...
}

↓

API route (app/api/orders/route.ts):
  - Zod validates shape, NOT content
  - Delegates to createOrder()

↓

createOrder() (lib/orders.ts):
  - Computes subtotal from items[i].price × items[i].quantity  ← TRUSTS CLIENT
  - discountAmount = input.discountAmount                      ← TRUSTS CLIENT
  - deliveryFee = input.deliveryFee                            ← TRUSTS CLIENT
  - tax = discountedSubtotal × 0.0625                          ← hardcoded rate (server-side, good)
  - total = discountedSubtotal + tax + deliveryFee
  - Inserts order + order_items into DB

↓

POST /api/payments/intent:
  - Reads order.total from DB                                  ← garbage-in, garbage-out
  - Creates Stripe PaymentIntent with that amount
```

### Price Source Map (Authoritative vs. Client-Trusted)

| Component | Current Source | Authoritative Source | Status |
|-----------|---------------|---------------------|--------|
| Product prices | Client (cart → Zustand → API) | `products.price` (DB) | ❌ Not verified |
| Service prices | Client (cart → Zustand → API) | `services.price` (DB) | ❌ Not verified |
| Promo discount | Client (via `/api/promo/validate` once, stored in Zustand) | `promo_codes` table (DB) | ⚠️ Validated once, not re-verified at order time |
| Delivery fee | Client (Mapbox geocoding + distance) | Server config + Mapbox | ⚠️ Can be called from server but isn't |
| Service add-on fees | Client (hardcoded `DELIVERY_SERVICE_OPTIONS`) | Same config (`lib/types.ts`) | ⚠️ Can be computed server-side |
| Tax | Computed server-side (`discountedSubtotal × 0.0625`) | Hardcoded `TAX_RATE = 0.0625` | ✅ Already server-side (but uses client-trusted subtotal) |
| Total | Computed server-side from client-trusted inputs | Should be fully recomputed | ❌ Garbage-in, garbage-out |

#### Phase 2: Server-side verification function (New file)

**New file: `lib/pricing/verify-cart.ts`**

```typescript
interface ClientCartItem {
  productId: string;        // UUID from products table
  quantity: number;
}

interface VerifiedCart {
  items: VerifiedItem[];
  subtotal: number;
  discountAmount: number;
  deliveryFee: number;
  taxAmount: number;
  total: number;
  promoCodeId: string | null;
  promoCode: string | null;
  freeShipping: boolean;
}

interface VerifiedItem {
  productId: string;
  name: string;
  slug: string;
  price: number;
  quantity: number;
  salePrice: number | null;
  imageUrl: string | null;
  preorderBatchId: string | null;
}

async function verifyCart(
  supabase: SupabaseClient,
  clientItems: ClientCartItem[],
  promoCode: string | null,
  deliveryMethod: 'pickup' | 'delivery',
  deliveryAddress: { street, city, state, zip } | null,
  userId: string | null
): Promise<VerifiedCart>
```

Logic:
1. Fetch product prices: `SELECT id, name, slug, price, sale_price, images, stock_status FROM products WHERE id IN (...)`
2. Build price map. Verify all product IDs exist. Fail if any missing.
3. Compute subtotal from DB prices (sale_price ?? price) × quantity. **Ignore client prices entirely.**
4. Validate promo code server-side (re-call `validatePromoCode()` — re-verify all conditions at order time, not just once during checkout UI).
5. Compute discount amount from promo code using subtotal.
6. Compute delivery fee: if pickup → 0; if delivery → call `getDeliveryQuote(address, services)` or `calculateDeliveryFee()` from `lib/storefront/delivery.ts`.
7. Compute tax: `Math.round(discountedSubtotal * TAX_RATE * 100) / 100`.
8. Compute total: `subtotal - discount + deliveryFee + tax`.
9. Return `VerifiedCart`.
