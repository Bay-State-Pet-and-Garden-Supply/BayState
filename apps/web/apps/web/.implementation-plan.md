# Implementation Plan

## Goal
Make `apps/web` boot locally with Supabase seed data, safe local Stripe checkout, docs, and tests that cover pickup and card payment flows.

## Current Status
- `supabase/config.toml`: present. Migrations and seed are enabled; local ports are standard (`54321` API, `54322` DB, `54323` Studio, `54324` Inbucket). Auth URLs are wrong for the documented localhost flow: `site_url` is `http://127.0.0.1:3000`, and `additional_redirect_urls` only includes `https://127.0.0.1:3000`.
- `supabase/seed.sql`: missing, but referenced by `[db.seed].sql_paths = ["./seed.sql"]`; `supabase db reset` leaves storefront/admin without local fixture data.
- Migrations: 175 timestamped migrations exist through `20260510200000_sync_trigger_queued_status.sql`. They already create categories, pet types, products, product storefront settings, facets, orders, services, and site settings. Do not edit existing migrations; add new timestamped migrations only.
- `.env.local`: local copy currently points at hosted/Vercel-style values. Treat as unsafe for local dev. Do not commit real secrets. Local docs/templates must force localhost Supabase and Stripe test-mode values.

## Risks
- Direct `auth.users` seeding can break if Supabase local auth schema changes. Validate immediately after `supabase db reset`; fall back to documented manual local admin creation if needed.
- Existing `.env.local` contains hosted/Vercel-style secrets. Do not copy into docs or seed. Rotate any exposed keys if they were committed or shared.
- Stripe API version string must be verified against installed `stripe@^20.2.0`; changing it may affect webhook object shapes.
- Adding checkout tokens touches checkout/order API contracts; update all tests and any mobile/API clients that call `/api/orders` or `/api/payments/intent`.
- Webhook and client payment-complete can race. Shared reconciliation must be idempotent and avoid duplicate order events/payments.
- Guest order confirmation pages are currently accessible by order ID. This plan secures payment mutation routes, not confirmation-page privacy.
- `supabase db reset` replays all migrations; old migrations may fail independently of new seed work. Do not patch applied migrations unless explicitly approved; add forward fixes.

## Rollback Plan
1. Revert route/component/lib changes for Stripe/payment flow.
2. Drop new local-only seed changes by clearing or reverting `supabase/seed.sql`; run `supabase db reset`.
3. Revert new package scripts/docs/env examples if they block dev.
4. Add rollback migration if DB changes already applied remotely/local shared DB:
   - Drop `stripe_webhook_events`.
   - Drop `order_payments.stripe_event_id`.
   - Drop `orders.checkout_token_hash` and `orders.checkout_token_expires_at`.
5. For local only, fastest rollback is `supabase stop --no-backup`, remove local volumes if needed, then checkout previous branch and `supabase db reset`.
