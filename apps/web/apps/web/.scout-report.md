## 4. Current Stripe Payment Flow

### Flow (from code):
1. **Checkout Client** (`checkout-client.tsx`) submits order:
   - Pickup flow: POST `/api/orders` → creates order with `payment_status: 'unpaid'`
   - Credit card flow: 
     a. POST `/api/orders` → creates order with `payment_status: 'authorized'`
     b. POST `/api/payments/intent` → creates Stripe PaymentIntent → returns `clientSecret`
     c. `PaymentForm` mounts Stripe Elements with `clientSecret`
     d. User submits card → `stripe.confirmPayment()` with `redirect: 'if_required'`
     e. On success: POST `/api/orders/[id]/payment-complete` → updates `payment_status: 'paid'`, logs event

2. **Webhook** (`/api/payments/webhook`):
   - `payment_intent.succeeded` → updates order to `paid`, inserts `order_payments` record, logs `order_events`
   - `payment_intent.payment_failed` → updates order to `failed`
   - `charge.refunded` → updates to `refunded` or `partially_refunded`, records refund in `order_payments`

### Stripe SDK
- API version: `2025-12-15.clover` (very recent — verify compatibility)
- `createPaymentIntent` converts amounts to cents (`Math.round(amount * 100)`)
- `constructWebhookEvent` verifies signatures
- `getOrCreateStripeCustomer` — looks up by email, creates if not found

### Payment methods accepted in checkout
- `'pickup'` (pay at store — no Stripe)
- `'credit_card'` (Stripe Elements)
- DB constraint also allows `'paypal'` and `'in_store'` but no UI for them

## 7. Checkout Architecture

### Checkout Steps (from `checkout-client.tsx`):
1. **Contact** — name, email, phone
2. **Fulfillment** — pickup or delivery (with address + delivery quote)
3. **Payment** — method selector then Stripe Elements or "Complete Order" for pickup

### Order creation flow:
```
checkout-client.tsx
  → POST /api/orders (creates order, status='unpaid' for pickup, 'authorized' for card)
  → if credit_card:
      → POST /api/payments/intent (creates Stripe PaymentIntent)
      → Stripe Elements confirmPayment()
      → POST /api/orders/[id]/payment-complete (updates to 'paid')
  → if pickup:
      → redirect to /order-confirmation/[id]
```

### Webhook fallback:
- Stripe webhook also handles `payment_intent.succeeded` — so if the user closes browser after payment, the webhook catches it and updates the order.

## 9. Risks & Mismatches

### Critical
1. **Turbo `test` depends on `build`** — running `bun run test` or `bun run web test` via Turbo will trigger a full build first. Use workspace-level test directly: `cd apps/web && bun run test` or `node scripts/run-jest.cjs` to skip the build.

2. **Root `vercel-build` script unused** — The root `package.json` `vercel-build` runs `cd apps/web && next build` but `vercel.json` at root runs `bun run build` (Turbo). The web app's `vercel.json` also runs `bun run build`. Vercel's monorepo settings determine which `vercel.json` applies.

3. **Supabase seed file may be missing** — `config.toml` references `./seed.sql` but only `seed-a11y-test-data.sql` and `seed-scraper-configs.sql` exist. Fresh `supabase db reset` may fail or have no seed data.

4. **Stripe API version `2025-12-15.clover`** — This is a very recent API version. Verify all Stripe calls (especially `payment_intent.create`, `webhook.constructEvent`, `ephemeralKeys.create`) work with this version. The `as Stripe.LatestApiVersion` cast bypasses TypeScript checking.

### Medium
5. **Payment method enum mismatch** — DB constraint allows `'pickup', 'credit_card', 'paypal', 'in_store'` but TypeScript `PaymentMethod` type also allows `'paypal'` and `'in_store'`. No UI or handler exists for these — webhook handler's `mapPaymentIntentStatus` doesn't handle them.

6. **`createOrder()` hardcodes `source_type: 'web'`** — In `lib/orders.ts`, `createOrder` always sets `source_type: 'web'`, even for admin-created or imported orders. The `CreateOrderInput` type doesn't expose `sourceType`.

7. **Delivery address not persisted** — `createOrder()` sets `delivery_address_id: null` with comment "Create via separate table if needed". Address is sent in payload but never stored in `addresses` table.

8. **`updateOrderStatus()` in `lib/orders.ts`** uses `Order['status']` type (`'pending' | 'processing' | 'completed' | 'cancelled'`) but this column in the DB is `text` with no CHECK constraint in current schema. The TypeScript type doesn't match the more granular `payment_status`/`fulfillment_status` enum system.

9. **Error handling: payment-complete route fetches PI** — If `order.stripe_payment_intent_id !== validatedData.paymentIntentId`, it calls `retrievePaymentIntent` to check status. This adds an extra Stripe API call on every payment-complete. Could be optimized/simplified.

### Low
10. **README outdated** — Shows `npm install`, `npm run dev`. Should be `bun install`, `bun run dev`.

11. **Env var naming** — `config.ts` reads `SUPABASE_URL` and `SUPABASE_ANON_KEY` (without `NEXT_PUBLIC_`) but `.env.local.example` only documents `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`. The fallback chain in `config.ts` handles both, but the example file doesn't show the non-public variants.

12. **`env-used.txt` has duplicates** — e.g., `VERCEL_URL`, `NEXT_PUBLIC_VERCEL_URL`. Not a bug but confusing.
